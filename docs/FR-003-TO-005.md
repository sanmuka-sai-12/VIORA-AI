# FR-003–005 — Narration, summaries and assessment

**Priority:** P0 | **Design status:** selected for build | **Implementation status:** not started

These requirements complete the teaching experience around the animated lesson. All three must refer to the exact approved outline and final lesson version. A regenerated scene or corrected narration cannot leave the summary and questions pointing at stale content.

# FR-003 — Narration and synchronization

## Required behavior

Generate a voice track for the lesson, synchronize it with the diagrams and scene actions, and display timed keywords, captions and labels. Speech should describe the visible explanation rather than run as an unrelated audio track.

The first build can support one tested language and a small set of voices. FR-007 extends the same contract to multiple languages.

## Design

Use a **two-pass timeline**:

1. In the storyboard pass, store the draft script alongside each scene and write named cues such as `mass_constant`, `force_increases` and `acceleration_changes`.
2. Generate TTS audio from the reviewed script. Record the actual duration, provider metadata, voice and language.
3. Obtain timestamp alignments when the provider supplies them. Otherwise align the known script to the audio using an evaluated aligner; do not invent word-accurate timestamps from character counts.
4. Resolve the semantic anchors into times; set scene lengths, motion offsets and reading pauses from those times.
5. Render the final timeline, produce WebVTT captions, and verify the audio/video/cue durations.

The underlying media manifest must keep `scene_id`, `script_version_id`, `audio_version_id`, locale, actual duration, cue timestamps, caption path and final rendered-media ID. The player must use the **published** manifest, not whatever timing draft happens to be newest.

## Checks

- Audio is understandable; the script does not claim an action that never appears.
- Captions contain the spoken teaching content and are in sync with the audio.
- Important labels appear while they are being explained.
- A changed script produces a new audio/timing version and marks downstream media stale.
- Unsupported voice or provider failure gives a clear error and a bounded retry path.
- A media probe confirms a playable file, expected duration and no missing audio track.
- Access is checked before generating and before publishing media from protected material.

**Open:** model/provider and TTS voice IDs, supported languages, alignment method, numerical drift tolerance, audio codec and caption QA tools. See [TECH-STACK.md](TECH-STACK.md) for the initial SDK, not a fixed speech model.

# FR-004 — Chapter summary and key points

## Required behavior

After a lesson is generated, produce a useful revision sheet: a brief explanation, important concepts, formulas when present, learning outcomes, key takeaways and quick review notes. It must not present a point as covered if the finished lesson never explained it.

## Design

Generate the first summary from the approved `LessonOutline` and its evidence references. Then check it against the **published scene and narration coverage**. Keep two flags where needed: `supported_by_source` and `covered_in_lesson`. Source-supported material omitted from the video may be shown as a *source note* if clearly labeled, not disguised as a video takeaway.

Store a `SummaryVersion` with the source outline ID, lesson publication ID, concept refs, optional formula/unit metadata, reading level and a validation result. A correction creates a new summary version.

A useful first output is one short overview, five to eight key points where appropriate, a formulas block for relevant subjects, and a revision checklist. These numbers are presentation targets, not rigid requirements for every chapter.

## Checks

1. Every key point links to a known approved concept; evidence refs are valid where the input supports them.
2. Formula signs and units agree with the approved material.
3. The generated summary does not describe a removed or superseded scene as if it still exists.
4. A topic-only lesson identifies inferred content rather than fabricating textbook citations.
5. Editing or republishing the lesson causes a consistency check before the summary can be republished.
6. The teacher can review or revise the summary without modifying the original source or outline.

**Open:** length by learning level, formula formatting, downloadable format and how much teacher editing is offered in the first UI.

# FR-005 — AI-based assessment generation

## Required behavior

Produce concept-linked questions after the lesson, including MCQs and concept checks. A learner submits an answer and receives a score or formative feedback with a short explanation.

Correctness matters more than question count. A plausible-looking MCQ with the wrong key is not acceptable.

## Design

Create a **question blueprint** before generating the questions. The blueprint says which learning objectives to cover, what difficulty is intended, which formats are allowed and how many questions are needed. Generate items against the approved source concepts and the actual lesson content.

A question record needs: stable item/version ID, lesson version, objective/concept references, stem, answer options if applicable, correct answer, explanation, difficulty label, source evidence, quality status and grading method.

The generation flow is:

1. Build a small objective coverage blueprint.
2. Generate candidate questions and explanations.
3. Reject duplicate, ambiguous or unsupported questions.
4. Check each correct answer against the source and explanation. For numerical problems, use deterministic rules or solvers where available; record uncertain checks for teacher review.
5. Publish only accepted questions under an immutable `AssessmentVersion`.
6. Send **student-safe question fields** to the browser. Keep the key/rubric private on the API.
7. Grade MCQs and short fixed-answer checks deterministically. Show the explanation after submission. Treat open-ended answers as formative feedback, not high-stakes automatic grades in P0.

For offline lessons, practice questions may include local answer material, but offline results are **not** trusted as authoritative exam grades. FR-010 will sync learner events with deduplication.

## Checks

- Every published question maps to at least one approved objective and the lesson version used.
- A deliberately incorrect key or conflicting explanation is caught or held for review.
- The API does not return the correct answer before the learner submits.
- Repeated attempts do not create duplicate events under the same attempt/event key.
- A teacher can view the verification status and revise or remove an item.
- Revoked or superseded questions cannot be newly assigned.
- Feedback quotes the correct explanation, not a freeform model guess at grading time.

**Open:** question counts, blueprint weights, proficiency rules, written-answer rubric policy, question bank reuse and anti-cheating measures appropriate to the use case.

## Shared dependency rule

```text
Approved outline
   ├─> Scene plan ──> script ──> audio/timing ──> final video
   ├─> Summary draft ─────────────────────────> published summary check
   └─> Question draft ────────────────────────> published quiz check
```

The publication manifest points at one consistent set of versions. If narration or a scene changes, the system marks affected media and any lesson-dependent summary/assessment as needing revalidation. This is a dependency check, not an unconditional regeneration of every file.
